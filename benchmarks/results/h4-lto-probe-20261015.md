# H4 compiler pilot — retain the existing build

**Do not integrate fat LTO.** All **44/44 layouts** pass independent native
validation, but the small Chrome improvement comes with worse Firefox results.
Production retains thin LTO, the original generated bindings and the original
built site. H4 remains open; completed milestone weight stays **45%**.

| Browser | Valid thin / fat | Median material change, fat vs thin | Median charged-work-rate change |
| --- | ---: | ---: | ---: |
| Chrome 155.0.8059.41 | 11 / 11 | −0.045601% | +0.325196% |
| Firefox 157.0 | 11 / 11 | +0.094779% | −3.552800% |

Negative material change is better; positive work-rate change means more charged
search work per actual solver second. Firefox's worst material change is
**+3.365375% on `m-sign-4`**. Ten of its eleven work-rate comparisons are lower.
Chrome's changes are mixed across jobs. These single-seed observations do not
establish a statistically reliable speed effect or show that fat LTO is always
worse; they do not justify changing the default.

Charged work is an existing fixed-coefficient proxy, not a direct CPU-cycle
measurement. Different time-limited trajectories can change the mix of operations.
Consequently the work-rate comparison is diagnostic, not proof that an individual
kernel became faster or slower. The material numbers here compare compiler
variants with each other, not with the native H4 reference.

## Fixed method

The [plan](h4-lto-probe-20261015T211442Z/plan.json) declares the same eleven H4
development jobs, seed 0 and 60 seconds per job. Every job uses its own fresh
browser worker, at most eight concurrently. Browser process trees retain physical
CCD0 CPUs 0, 2, 4, 6, 8, 10, 12 and 14; all four batches report zero affinity
deviations. Chrome runs thin then fat; Firefox reverses that order. Each batch
takes about 122 seconds and independent validation runs after the browser exits.
This is not a repeat of the earlier SIMD or allocator experiments.

The sole build lever is `CARGO_PROFILE_RELEASE_LTO=fat`, overriding the existing
thin-LTO release profile. Rust 1.98.1 and the locked wasm-bindgen 0.2.129 build
the same product source and dependencies. The separate Cargo target directory,
bindings and site are under ignored local output/cache directories. Build work
runs on CCD1. The original generated bindings are restored before measurement;
the production site is never overwritten. Source, CLI, input and site guards pass.

The native validator agrees with every saved metric exactly. All eight example
outputs also validate against their actual library/request, preserving all
components and curve clearances. There are no failed, missing or discarded
attempts. The candidate WASM is **3,529,117 bytes**, just 973 bytes larger than
the current **3,528,144 bytes**. Reported memory is final WASM linear memory;
it is not a browser peak-working-set or H4 scale measurement.

The Windows processor report is 4,201 MHz. The ACPI temperature query was denied,
so no die-temperature value is claimed. The measured session is about eight
minutes, within the four-hour limit and the eight-solver cap.
